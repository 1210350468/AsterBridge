# Release validation

CI proves that the runtime builds, the launcher starts, and native packages pass their smoke
contract on macOS, Windows, and Linux. It does not prove an authenticated ChatGPT session, a live
MCP connector, or a complete Codex turn. A release candidate is not ready until those account-bound
flows are exercised manually on the platforms below.

## Required evidence

Record the release version, operating-system version, install path (`clean` or `upgrade`), ChatGPT
plan, Codex version, result of each check, and a redacted Activity log for every failure. Never
capture cookies, tunnel IDs, API keys, bearer tokens, or prompt contents.

The native package smoke is a separate prerequisite. On Windows it must use the completed NSIS process rather than a partial installation, verify `resources/runtime/runtime/bun.exe`, the runtime launcher and manifest before app startup, execute the durable installed runtime, and require the Launcher readiness marker to report tray availability. A valid Windows installation may exceed two minutes on slower storage; the smoke uses a bounded ten-minute installer budget so its own timeout cannot manufacture a half-installed package failure.

The root core suite must run through `bun run test`, which intentionally executes every `tests/*.test.ts` file in its own deterministic short-lived Bun process. Do not replace this with one giant `bun test tests/*.test.ts` process in CI or Release workflows: Bun 1.4.0 can crash at the runtime level before test assertions finish. The runner must enumerate the complete test directory. It may retry only explicit Bun runtime-crash exit codes, at most twice by default; assertion/test failures such as exit code 1 must fail immediately and are never retried. On Windows + Bun 1.4.0 only, the eight short-lived named-pipe cases in `turn-broker-lifecycle.test.ts` are skipped because the Bun runtime can terminate before assertion reporting; Unix still runs those exact cases, while Windows broker behavior remains covered by server lifecycle, Full Harness, retained-compaction, DEV-driver, Launcher, and packaged-runtime tests.

## Windows 11 gate

Run this list on a maintained Windows 11 x64 machine with a real ChatGPT account. Treat it as a first-user journey, not just an internal feature checklist:

1. Install the packaged launcher on a clean Windows profile by following only `README.md` and `docs/quick-start.md`. Prove that no undocumented terminal step is required and that the embedded Bun runtime starts.
2. Prove network onboarding before model setup: with no explicit proxy, confirm **Automatic** reports the expected source; then test **Direct** and a valid **Custom** HTTP proxy. Verify local `127.0.0.1:17841` and Roxy `127.0.0.1:50000` stay bypassed through `NO_PROXY`, the managed daemon/tunnel restarts safely, and Doctor distinguishes `network-chatgpt` / `network-openai` failures from local Bridge health.
3. Prove the simplest embedded-browser path: sign in, reach a usable Temporary Chat composer, run **Doctor**, install the model route, restart Codex once, and complete the documented `WEB_OK` Browser-only turn.
4. Prove the recommended Roxy path from a clean Launcher state: save a Profile ID/data root, run Doctor, and complete one Browser-only turn through that exact Profile without copying cookies or browser state. Confirm AsterBridge proxy settings do not silently rewrite the Roxy profile's own proxy configuration.
5. Close the configured Roxy Profile completely, enable auto-open, and prove that Doctor reports either a reachable Profile or a healthy Local API ready to auto-open it. Start a turn and prove the Profile opens automatically instead of producing an unclassified stream disconnect.
6. During a live Roxy turn, prove Launcher **Live Preview** shows a real task frame/stage and **Take control** activates the matching Roxy task window without creating a second CDP owner. Let the same turn finish successfully afterward.
7. Prove every account-available ChatGPT Web effort appears exactly once in Codex without removing native models. A WebSocket `426` followed by successful HTTP/SSE fallback must not be reported to the user as a setup failure.
8. Prove Full-mode local tools through the primary MCP transport. Configure a fresh `Codex Native3` connector, run **Verify runtime**, complete one harmless MCP local-tool turn, and prove ChatGPT can remain in the same response across multiple dependent tool calls while outer Codex returns the real results. Start a fresh Full-mode Codex task whose outer registry exposes image generation and prove `image_gen__imagegen` reaches outer Codex, returns a real tool result, and writes the artifact under Codex `generated_images`. Retired `Codex Native` / `Codex Native2` identities must produce an explicit migration error rather than being silently reused. A ChatGPT first-party image result without an outer-Codex tool call/result is a release failure. The connectorless Responses bridge is an experimental fallback only: test it separately when desired, but its success does not replace the MCP stable-release gate and it must never be selected without explicit opt-in. Attach eight real images to a separate Web turn and prove all eight tiles complete, the adaptive attachment/send budgets are logged, submission is accepted without a duplicate retry, and the answer completes. Finally verify direct visual understanding, close every Temporary Chat page, and prove the resumed Codex thread can still answer a previously unstated visual detail from a historical image without attaching it again.
9. Prove conversation continuity independently of Temporary Chat lifetime: place an exact sentinel in a fresh Web thread, recover it on the next turn, close every Temporary Chat page and recover it again, then restart Launcher/daemon and recover it a third time. Verify retained continuation sends only the canonical suffix while a live page exists and falls back to bounded full-context replay after page loss/restart. Open enough completed Web threads to fill the five physical-page budget and prove the next new thread evicts the least-recently-used idle retained page; five genuinely active browser turns must still block a sixth. Record the Roxy ChatGPT-page count before and after Browser check / session inspection / connector verification and prove maintenance does not leave another page behind; at five retained surfaces it must evict one idle retained page instead of opening a sixth. Then drive a chat past the compaction threshold and prove that its handoff/retirement closes the superseded retained surface and continues without a duplicate/orphaned browser turn.
10. Cancel a running turn from Launcher and cancel another from Codex; prove neither recreates a browser page nor leaves HTTP/browser activity counters busy.
11. Quit/reopen the launcher around an idle runtime and around an active-turn cancellation. Prove stale-owner recovery is bounded, the saved browser/Roxy/proxy configuration survives, and the Responses daemon returns to `127.0.0.1:17841` without launching duplicate owners.
12. Disconnect the bridge and prove that the exact previous Codex route is restored. Reconnect it and prove existing private MCP/Roxy credentials are reused rather than exposed or replaced.
13. Upgrade from the previous public release. Prove Launcher state, Roxy/proxy settings, browser state, Codex settings, and private MCP configuration survive; prove old `Codex Native2` local configuration is migrated to the required `Codex Native3` identity with a clear user action.
14. Run **Settings → Run diagnostics** in at least four failure states (bad proxy/public upstream unreachable, closed Roxy without auto-open, invalid/unreachable Local API, stopped Tunnel). Confirm each failure points to the correct recovery action. Use **Copy diagnostic summary** and verify the clipboard text contains no API credentials, proxy credentials, token, cookie, full turn token, prompt body, or Doctor `detail` field.
15. Open the GitHub bug form from a clean browser and verify its Quick Start/Troubleshooting links resolve, the required fields match the support workflow, and the security checklist prevents accidental credential sharing.

Any failed or unexecuted item blocks a stable release. An alpha may ship with a named failed item
only when the release notes describe the limitation and recovery path explicitly.

### v3.0.30 local result

Maintainer validation on Windows 11 x64 on 2026-09-04 used the exact packaged/installed 3.0.30 artifact with the authenticated RoxyBrowser profile, `Codex Native3`, and the primary MCP Full Harness transport. Final installed Doctor reported configuration valid, Roxy profile reachable, Codex route installed, Launcher ownership healthy, Responses proxy healthy on `127.0.0.1:17841`, ChatGPT/image upstream probes reachable, Tunnel runtime key stored privately, Launcher-owned Tunnel healthy/ready, and explicit browser verification confirmed `ChatGPT connector "Codex Native3" is available in the configured external browser.` Production health returned to `active_http_turns=0` and `active_browser_turns=0` after the release soak.

Exact-source verification passed: Core **42 / 42**, Launcher **210 pass / 0 fail / 1 Windows-inapplicable skip**, TypeScript PASS, renderer production build PASS, `RELOCATABLE_RUNTIME_SMOKE_OK`, and `bun audit` reported **0 vulnerabilities / 106 packages**. The exact Windows package `asterbridge-3.0.30-win-x64.exe` is **151,544,880 bytes** with a **158,030-byte** blockmap, SHA-256 `255FE4F4DC16F5D064E4792319501099C2235F6A63E5525A4ADDDC68B6AF33B4`, and passed `PACKAGED_LAUNCHER_SMOKE_OK win32/x64`.

The installed long-chain regression that exposed 3.0.27 replay was rerun after the 3.0.28 deferred-subagent fix: the pre-subagent shell and image-view stages executed once, deferred spawn reached outer Codex, the child completed through wait/close, and the parent finished without rebuilding the browser session or replaying earlier successful tools. Explicit Launcher cancellation was then tested against a real already-running local shell. AsterBridge cancelled Web/HTTP ownership and tombstoned the native execution key; the already-started outer-Codex tool was allowed to finish once, while five subsequent Codex reconnect attempts were rejected as `turn_cancelled` before browser creation. Rollout evidence contained **1 function call / 1 command completion** for the cancelled command and final activity returned to 0/0.

Native retained compaction also passed against Codex 0.150.1. Two retained Web turns compacted into a real `contextCompaction` on the same owner and the full E2E script returned `ASTERBRIDGE_CODEX_COMPACTION_OK` with `sameOwner=true`. The resulting compacted thread was resumed and `Codex Native3` executed `Write-Output POST_COMPACT_MCP_330_OK` with exit code 0, proving MCP tool work continues after replacement-history compaction. 3.0.30 keeps structured one-shot MCP compaction handoff authoritative, but if the dedicated retained compaction response completes with a valid checkpoint and current ChatGPT skips that control call, AsterBridge allows only a short grace interval, revokes the one-shot control token, canonicalizes that exact retained-turn checkpoint, and rejects any late stale handoff.

A mixed Full-Harness soak completed shell → outer Codex image generation → native subagent spawn/wait/close → final answer in one parent task. The parent executed `Write-Output MIX330_SHELL_OK` once, emitted one `imagegen` call in namespace `image_gen` followed by completed extension output, wrote one **1254×1254** PNG (**825,948 bytes**, SHA-256 `19561F12D2CA53AFCFA7724DADC15B2C19D07BA6EB4F0BD50BA92791FE9E4E96`) under that parent thread's `generated_images` directory, completed the child agent, and returned `MIX330_OK`. A DevPilot control-channel 502 launched the test command twice as two independent root `codex_exec` processes with different Codex thread ids; each root completed independently with its own artifact. This is test-controller duplication, not same-turn AsterBridge replay, and must not be used as evidence for or against one-turn exactly-once semantics.

Concurrency soak reached five simultaneous browser turns and a sixth failed closed at the five-page safety ceiling. Under five-way MCP-tool pressure, ChatGPT Custom App/Tunnel produced intermittent upstream 502s before some calls reached AsterBridge's local TurnBroker; the local broker did not lose an accepted call, no orphaned test shell remained, all browser/HTTP ownership returned to 0/0, and Launcher crash/restart restored Full MCP, Tunnel readiness, Roxy reachability, and connector verification. Therefore the five-page limit is a browser/resource safety ceiling, not a guarantee that the upstream ChatGPT App/Tunnel can sustain five local-tool executions concurrently.

### v3.0.25 MCP-primary restoration

3.0.25 restores the release contract that existed before the connectorless experiment: MCP/`Codex Native3` is the primary Full Harness transport and the Launcher no longer advertises or automatically preserves Responses Full as the recommended tool path. The Responses direct-tool implementation remains available only through explicit advanced/CLI opt-in for experiments on accounts without custom MCP Apps. Stable promotion requires the MCP gate above; the 3.0.24 Responses results below remain historical fallback evidence, not a substitute for MCP validation.
